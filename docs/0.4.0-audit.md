# 0.4.0 改造起点与界面对照

界面截图均来自自建离屏 Qt 窗口与假数据，供评价操作布局，不是游戏兼容性证据：

- [改造前的常驻截图和参数界面](images/before-0.3.0.png)
- [v0.4.0 日常主界面](images/dashboard-0.4.0.png)

2026-10-14，基线提交 `9237990`，工作区起初干净。基线执行结果：218 项通过、1 项符号链接权限跳过，证据保存在本地 `artifacts/candidate-0.4.0/baseline-tests.xml`。这些数字只代表改造前版本。

首次操作原来需要选择窗口、等待三秒并切回、选择“按钮模板”类型、框选、预览、另行保存、选择模式并开始。再次使用可以载入 JSON 复用模板，但仍需重新选择当前目标。原主界面同时常驻截图、模板类型、原始分数、窗口身份及识别参数。

日常必要操作是配置选择、目标确认、运行模式、开始/暂停/继续/停止和一句状态解释。模板、范围、成功标志、参数、捕获方式、导入及路径应放到编辑或高级设置；原始分数、进程身份、坐标及捕获证据放入诊断。

原 `Engine._scene` 同时检查窗口几何、前台、移动和候选区域遮挡，提醒和点击都调用它。原 `WindowsBackend.capture` 用屏幕 GDI BitBlt，不能把非前台时取得的遮挡物像素视为目标自身画面。窗口身份核对包括 HWND、PID、进程创建时间和可执行文件；帧验证包括目标、本轮、时间和序列。输入仅经过 `Engine._execute`，在原生输入前消耗一次资格。

本版拆分只读捕获、识别、提醒和输入条件。采用固定版本 `windows-capture 2.0.1` 的 HWND WGC 捕获，保留真实源时间、源序列、接收时间和捕获代次；在捕获线程交接一份拥有内存的 BGR 图像。调用者仍收到客户区物理像素图像。GDI 仅作为明确的前台兼容方式。新依赖要求普通 `opencv-python`，因此项目虚拟环境由同版本 headless 发行包切换为普通发行包，避免两个包同时占用 `cv2`。

切回权限只来自本轮明确勾选，不写入配置。后台发现后最多请求一次正常前台切换；系统拒绝则只提醒。实际点击仍需独立核对前台、等待新画面、重新确认唯一按钮，并经过原有输入检查。向导使用临时状态，取消和采集失败不清除旧模板。

最初任务仅要求本地候选包；用户随后明确要求推送和 Release，因此本版完成检查后发布 v0.4.0。原生捕获、真实切回、真实输入和真实游戏兼容性分别记录，不用假测试或历史六格结论代替。

技术依据：[WGC HWND 互操作](https://blogs.windows.com/windowsdeveloper/2019/09/16/new-ways-to-do-screen-capture/)、[Microsoft 捕获指南](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)、[SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)、[windows-capture 源码](https://github.com/NiiightmareXD/windows-capture)。
